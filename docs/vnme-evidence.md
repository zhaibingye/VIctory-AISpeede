# VNME 实机与验证证据

这里记录当前实机基线和足以影响路线的对照，不按轮次追加。正确性与发布门槛见[VNME 架构](vnme.md)，实验与止损规则见[开发原则](development.md)，可复用的实现知识见[项目记忆](../MEMORY.md)。源码基线、实际运行的构建和记录提交是三件事。现有基线及此前的排除证据可回查 `4cce33f346c0a9b1d96913a1b35f0c8eab53a1fc` 与其 Git 历史。

## 当前实机基线

| 对象 | 实际运行的源码 | 到达阶段与记录 |
| --- | --- | --- |
| VNME | `89e6734` 上的本地诊断 `d4d37f60e3a87c53b2722603493dd5c9739daf66` | Windows Series S，继续提示有真实双层 `PresentX` 读回；确认提示后一次 A，首错仍是 `draw 15` 编码报 `MissingTextureContent`。旧构建 `8c7269a` 的精确绑定 PS 证据仍归该构建（记录 `d8b709c`）。 |
| 独立参考 `fxceless/victory-fork` | `2eade68cade9b2f8cd2511cc97328e83f58508c3`，干净源码锁定依赖离线构建，Rust 1.98.1、Windows x64 MSVC、dev、`diagnostics,blake3/pure` | 同一锁定 EXE 再次按 A 到语言选择，并经画面确认逐页完成默认首次设置、通过本地法律告示；停在要求用户确认隐私政策、同意服务条款的界面。不代为确认；尚未进入可控场景。原开场记录见 `4cce33f`。 |

- **可比条件。** 同一 Windows 机器、同一游戏入口（输入文件 BLAKE3 一致）与 Series S 配置，均直接 `run --execute --console series-s`。fork 用新存档、缓存和日志，未用 DLSS、帧生成、额外光追或 1440p 补丁；提示可见后用内置 `VICTORY_KEYS_FILE` 发一次映射到 A 的输入。运行时序、缓存初态、后端及诊断开销并非完全相同。
- **构建来源。** fork 实跑 EXE SHA-256 为 `5a2cf8ed2444fa65709b2d9850bf17300c2a486e22543b28ef71996aa66503ea`；独立重链接 PE 只差 COFF / Debug 时间戳和 CodeView GUID，代码和数据未变。未运行上游脚本或发布二进制。
- **独立基准的当前阻碍。** 新空数据与缓存下，内置输入逐项触发可辨识的菜单切换。进一步进入条款确认页时，两项均未勾选、确认不可用；约 25 秒后的送显路径读回仍为同一关卡，随后由采集者主动停止本轮实例。此构建的图像在同步 GPU 回读后、DXGI `Present` 返回前保存，未单独记录 `S_OK` 或该帧各层生产者。该结果证明首次设置和告示可操作，不证明可控 3D 或可玩。须由用户在隔离会话中自行审阅和决定；不写入同意状态、不跳过关卡，也不复用原存档。
- **结论边界。** 同机同入口并非必然无法显示按 A 后的开场。fork 通常用独立宿主 RTV，不经过 VNME 的旧色准入；其一般地址式创建（vtable 槽偏移 `0x428`）降低为 `COMMON`，有优化清除值但不把它当写入，槽偏移 `0x470` 仍被忽略。尚未对齐两边的同一颜色操作，不能推断 fork 有该目标的有效底图，或把它的放行当作修复。两边均未取得可控场景、十分钟可玩、游戏内性能或发布验收证据。

## VNME 拒绝处与关键排除证据

首错绑定为 slot 0 / subresource 0，读目标旧色；拒绝报告的 29、3840×2160×1、单 mip 来自**宿主资源描述**，不是实际 RTV 描述。归档没有存下完整来宾资源 flags 或实际 RTV 描述。没有已识别的同键前代或兼容字节来源（`13eee34`）。颜色目标为地址式创建，初始增强布局码 6，带优化清除值；目标范围内匹配 510 个同一 XMem section 的页（`df5dcfd`、`64dd795`）。这 510 页是按现有布局模型识别的候选范围，不是整个分配大小的实测。`94861f1` 与 `64dd795` 均通过开场 XMem 准入，后者未出现更早的上传快照冲突；两者仍在按 A 后遭遇同一颜色拒绝（记录 `8294e04`）。

| 已检验的假设 | 实际证据与不能推出的结论 |
| --- | --- |
| **已识别批内操作可以提供旧色** | `64dd795` 的未提交前缀 0–14 中，五个已识别原生写均非同目标；唯一匹配目标的增强屏障（第 14 项，无弃旧标志）不生产像素。`0x470` 的 ABI 与副作用未证。`b40a245` 的前缀无来宾字节复制、显式纹理上传或纹理复制；`8c7269a` 的前缀固定页计划中 10 张声明脏页也无目标命中。`8aa9317` 的 WARP 队列夹具确认同目标前置整面清除能供混合 draw 读取（真实 Fence 后核对像素），缺失、局部、后置清除不能通过；`5e59087` 进一步经来宾描述符录制确认换到异对象也不能通过。对照验证生产者门禁，不证明实机有生产者，也不独立证明来宾 ABI。 |

| **混合读者自身可消除对旧色的依赖** | `7174c48` 记录实际 RGB 与 Alpha 均用 `ADD(SRC_ALPHA, INV_SRC_ALPHA)`。`425a069` 的 WARP 对照中，不透明输出且整面覆盖才使该例结果与底图无关；相同 Alpha 但弃掉半面时仍依赖底图。`8c7269a` 以 DXIL 字节匹配确证诊断对应实际绑定 PS，输出分类为 `Unknown`，未证明 Alpha、覆盖或翻译错误（`d8b709c`）。不因签名、视口或此结果放宽准入。 |
| **创建或 XG CPU 复制暗中写了目标** | `812ceb9` 的 Windows 合成 section 对照表明：地址式创建与 RTV 创建保留映射字节，不发布原生颜色版本；布局转换和优化清除值不能让相同读者通过。`8b216e0` 的 HLE vtable 夹具证明：同形状默认 R_X 的有效 XG copy-in 返回 `E_NOTIMPL` 且不写，显式 row-major 对照可写。这不证明实机调过或没调过 XG 或其他 CPU 写入入口；不能用未见告警替代调用证据。 |

本仓的提交可用 `git show <SHA>` 核对；独立参考的本地补采提交不在本仓历史中。结果摘要与其实际运行源码分别保留，例如 `4cce33f:MEMORY.md`（fork）、`d8b709c:MEMORY.md`（PS 探针）、`c60b014:MEMORY.md`（前缀重放）；用 `git show` 读取历史快照。合成夹具、编译和实机是独立证据，不相互替代。

## 开场颜色内容交接

先按来宾创建描述、分配生命周期、实际 RTV/SRV 绑定、混合状态以及相对命令和提交顺序配对；不按 draw 序号、尺寸或虚拟地址配对。**能否找到 fork 在同一读者之前、对同一分配实际产生或保留有效旧色，而 VNME 没有等价处理的第一处操作？** 候选包括实体写入、对象重用、命令解释或后备交接，但必须能确认目标、覆盖范围与顺序。

一次有界的 fork 补采（基于 `2eade68` 的本地探针 `2bfeeb6`）复现 A 后的开场动画及语言选择，但没有输出符合严格筛选的 RTV 候选。筛选要求实际 RTV 格式与归档宿主资源格式一致；两者不等价，且探针没有运行时阳性对照。归档复核在两次独立参考实跑中都看到了按 A 后 `29 → 28` 的 RTV 格式转换报告，说明旧筛选会排除这种视图；转换记录没有绑定到具体读者，不能把它归给首拒目标。两次参考与 VNME 实跑在按 A 后有相同顺序的前五条来宾着色器首次绑定记录（阶段、容器长度、日志短哈希一致）；参考随后都多记了一条相同的 CS 首次绑定，VNME 首拒前没有这条记录。这只把两端缩到同一启动阶段，不证明该 CS 已分派或写到被拒目标，也没有把某条绑定唯一连到 `draw 15`。旧筛选无候选不证明 fork 未执行同一操作、无生产者或有有效底图。

独立开场基准中，来宾 `PresentX` 到交换链后台缓冲区已取得实像素对照。由锁定 fork 构建的本地诊断 `fdb5aac7c3adcba72e611c0176fa9b5771c737c0`（EXE SHA-256 `9fe4355fa2ed9f380eb0fca8086c0c4fe088c680ebb47cbe9d4ff1bdaee069f4`）在同机 Series S、可见提示后一次 A 的窗口内，读回同次送显的主层和宿主界面绘制前的后台缓冲区。有效的 21 个采样均经过实际双层合成、真实 GPU Fence 与 `DXGI S_OK`；两张早期样本 RGB 完全相同，动画样本的 2,073,600 个像素全部在 RGB 上不同，语言选择样本有 2,073,265 个不同。这排除“直接复制主层就等价于这两个样本”的解释；不证明混合公式符合真机，也不说明每一层由谁写入、是否存在同一 `draw 15` 读者或 VNME 是否送显了旧版本。

同一独立参考的元数据诊断 `e7cd10a32c421aaee584cd74860830bba14cbf80`（EXE SHA-256 `89649b9a0981abef6423aecfcca43875f222dbcd2def5c79e67e5ec1e25e9f3f`）复现了开场动画与语言选择。23 个双层样本（A 前 10、A 后 13）的生产历史，均按帧与真实 GPU Fence 对齐同次 `DXGI S_OK` 送显读回；合成列表中捕获了对实际后台缓冲区绑定的 draw 作为阳性对照。两层被实际读取的宿主对象生命周期 ID 跨这些样本均未变，因此不把参考能继续开场归因于已采样送显层的宿主换代；采样间的来宾分配交接以及未送显目标仍未被覆盖。在每个样本中，两个被合成器实际读取的宿主对象按生命周期 ID 对齐到各自的子资源 0；在同一 Direct Queue 上，实际 `R8G8B8A8_UNORM` RTV 的无矩形整面清除依次写入主层和叠加层，接着有叠加层 draw 候选，然后才送显。没有按资源尺寸、地址或来宾 draw 序号配对。

这是**原生整面清除为两层初始化**的实机正证，不把 draw 绑定当成覆盖证明，也不把主层无 draw 候选当成只有清除。探针未归因间接执行、UAV、CPU 字节生产或其它队列；手段不能证明最后一次像素写入、清除后的全部来源或两边对应同一个拒绝读者。因而优先验证有序的原生清除、叠加绘制与双层送显交接，不先把显式 CPU 上传当成开场修复。

Windows x64 硬件 D3D12 夹具已复现并修复一处不同的 `PresentX` 内容交接缺陷：整面清除生成的双层合成像素为 `[127, 0, 128, 255]`，无更新时保持不变。对同一叠加层用来宾 `WriteToSubresource` 写入整面 `[0, 128, 0, 128]` 后，旧实现在 `CopyResource` 之前送显仍为原色，但同源来宾 `CopyResource` 的目的纹理每个像素都已是新值。修复后，复制之前的合成即为 `[127, 128, 0, 255]`；保留同一内容版本号，观察到真实 Fence 后才发布其原生表示。两边都按真实双层合成、GPU Fence 与 `DXGI S_OK` 读回，并非由单层降级得出。该夹具只证明可精确寻址后备上的显式 CPU 版本交接，不证明任意持久指针写、未初始化内容或不明别名有效。

没有证据表明游戏开场的送显层使用该 CPU 写入路径。另一个 Windows x64 硬件 D3D12 夹具（`31348c0dd8cb73cea93f84c99c814efc7e5aaadf`）在 VNME 中用来宾 vtable 分别提交两层真实 RTV 的整面清除，再提交读取目标旧色的叠加 draw（裁剪至左半面），最后调用 `PresentX`。无中间 CPU 等待、CPU 纹理上传或单层回退。两层完成的原生版本分别为 1（清除）和 2（清除、draw）；真实 GPU Fence 与 `DXGI S_OK` 后，32×32 后台缓冲区的绘制区首像素为 RGBA `[127, 64, 128, 255]`，保留区首样本为 RGB `[0, 127, 128]`，按隔行隔列取样的 16×16 全部 RGB 样本均在预期值 ±1 内。该结果证明 VNME 对已定义的原生生产链能保留未绘制区域并按序送显，不证明游戏已经执行同样的链路。

最新 VNME 实机诊断（EXE SHA-256 `7c147f36e59a277deccf4c118841deec307b1ac5eb85ec9e120c249bd5a185eb`，Rust 1.98.1、Windows x64 MSVC、dev、`paged-title,diagnostics,blake3/pure`）在同机、同入口 BLAKE3、Series S 和独立缓存/数据的运行中，确认可见继续提示来自实际双层合成。提示样本在 Fence 864 和 `DXGI S_OK` 后读回；按同一宿主对象生命周期与子资源 0，对齐到 Fence 863 的主层、叠加层无矩形整面 `R8G8B8A8_UNORM` RTV 清除，随后是同一提交的叠加层索引 draw。两层实际绑定的来宾来源均为 committed、初始增强布局 3、带优化清除值；这里的底图来自实体清除，不是初始值。叠加 draw 槽 0 的宿主混合为 RGB `ADD(SRC_ALPHA, INV_SRC_ALPHA)`、Alpha `ADD(ONE, INV_SRC_ALPHA)`。独立参考的可见提示样本也有同一类清除—绘制—合成顺序，但参考未捕获完整来宾创建描述和该 draw 的混合态，不能认定是逐操作同一配对。

可归因到当前送显实现的差异是实际后台缓冲区：VNME 按消费层的最大宽高取 3840×2160，参考按主层取 1920×1080；两端合成读回证实尺寸不同。这是宿主输出尺寸策略，不是某个来宾颜色生产者不同的证据。确认提示后，VNME 接收一次内置 A，约 1.7 秒后首拒；没有取得 A 后成功双层读回，不推断没有后续送显或没有生产者。故不修改已验证的提示清除链，也不把改后台缓冲区尺寸当作首错修复。

现有证据没有可归属到首拒读者的分配交接，停止重复首错配对与单边拒绝采样。保留 VNME 拒绝作对照，沿独立基准推进到可复现的可控场景，再按已证的内容交接逐项接入统一内存。只有发现同一读者及同一分配上的实际生产者，才重开首错验证。字节恢复仍须独立证明同一分配的初始化、主平面、压缩/元数据契约和读者应见的权威版本；原生路线仍须证明前置生产者及其覆盖。独立基准不是生产回退；不放宽旧色门禁、不伪造 Fence、不采用 Shadow 回退。
