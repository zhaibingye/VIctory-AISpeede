# VNME 第三代架构与开发路线

本文定义 VNME 的正确性要求、代码入口和 Windows 验收门槛。如何选择路线、验证和止损，见[开发原则](development.md)；实际跑过什么、仍缺什么证据，见[实机与验证证据](vnme-evidence.md)；可复用的实现知识见[项目记忆](../MEMORY.md)。[旧统一内存文档](unified-memory-engine.md)仅供回查历史。

## 目标与选用路径

让 Series S 游戏在 Windows 上保持可观察行为等价，优先覆盖 RTX 3060 Laptop 6 GB、16 GB RAM、i5-11260H 一类设备。保留 x86-64 原生执行、Loader、Xbox HLE、着色器翻译和管线预编译。能用宿主操作保持等价，就不复刻来宾的实现过程；确需由 CPU 或别名访问精确字节时，在同一引擎内提供字节兼容表示。

生产方向只有一套 VNME。**当前 Windows 构建仍须显式启用 `paged-title`**，仓库还有旧渲染代码，不能把现状写成已完成默认切换。允许重构资源模型、改换实现路径或用外部实现对照；模块分层不是硬约束，来宾可观察行为和以下不变量才是。VNME 失败时不静默回退 Shadow Buffer，不跳过真实写入、不伪造完成、不拿同尺寸纹理或零填充冒充应有内容。未证明的操作须明确报告或拒绝。

## 正确性不变量

- **物理身份不等于内容权威。** 来宾后备以 64 KiB 页跟踪物理身份，别名按实际后备识别；同 VA 重绑、宿主对象换代都不能沿用未经证明的旧内容。Pin 保活的是后备，不是字节快照。原生纹理不必按页存放；缓存、旧副本和在途快照可以暂存，不能成为另一份权威。
- **只发布有证据的版本。** 按对象、子资源和真实覆盖范围跟踪生产者。读旧色前，必须知道来源、布局、范围以及写与读的顺序；屏障和优化清除值都不是像素写入。局部写除非明确弃旧，否则须保留未写部分。只有证明后续访问不依赖旧内容，才可省去其读取或恢复。只凭本次写入建立整面版本，须证明写全；更新已有有效内容时，还须证明未写部分得以保留。裁剪和视口铺满不证明实际覆盖。
- **分别处理批内、在途和已完成。** 同一对象子资源的查询次序是本批 `pending`、同队列在途 `SubmittedTail`、已完成版本。录制顺序不替代提交顺序，不比较不同对象的局部版本号来判断谁更新。观察到真实 GPU Fence 完成、且必要的字节合并成功后，才发布已完成内容并按依赖解除保活。
- **按需保持可见性。** 只给真实消费者准备所需范围，避免无意义的上传和回读。优先由主 Direct Queue 顺序解决 GPU 内部依赖，让无依赖工作重叠。CPU 原生指针读取 GPU 权威数据前，必须在真实访问或已知同步点保证可见；当前不能声称任意 CPU 访问均已覆盖。

## 实现职责与代码入口

下列入口按职责索引，不规定 crate 数量或改动边界，也不代表每条路径都已实现或验收。GPU 文件名均相对于 `crates/victory-gpu/src/`；内存文件名相对于 `crates/victory-memory/src/`。

| 职责 | 当前核对入口 |
| --- | --- |
| 统一地址、物理别名、后备保活 | 内存 `guest.rs`、`physical.rs`、`virtual_pages.rs`；GPU `title_backing.rs`；HLE `crates/victory-hle/src/modules/xmem.rs`。 |
| 对象生命周期、原生与字节表示 | GPU `resource.rs`、`page_resource.rs`、`page_texture.rs`；`crates/victory-formats` 提供已建模的布局与转换，不能代替实际分配的布局证明。 |
| 来宾操作与主机执行 | GPU `list.rs` 录制，`page_draw.rs`、`page_dispatch.rs`、`page_view.rs` 处理画、算、视图与访问；`crates/victory-shader` 翻译着色器。 |
| 权威、一致性与异步提交 | GPU `page_queue.rs` 编码、提交和退休，`page_resource.rs` 跟踪内容，`title_timeline.rs` 跟踪 Fence；内存 `authority.rs`、`coherence.rs`、`timeline.rs`。 |
| 准入、驻留与复用 | GPU `working_set.rs` 采宿主压力，`residency.rs`、`page_slabs.rs` 管 GPU 侧驻留和分配；内存 `budget.rs`、`budget/`、`residency.rs`。 |
| 原生资源缓存 | `crates/victory-pipeline`、`crates/victory-shader`、GPU `shader_cache.rs`。现有缓存不代表已有完整纹理或几何缓存；新缓存须校验内容、格式及转换版本，必要时匹配设备和驱动，不持久化不透明的显存布局。 |

## 预算与驻留

Series S 的 **10 GiB 逻辑统一内存、7,776 MiB 标题报告值**不变。宿主自适应预算不是取消安全上限，也不是预占固定的 10 GiB RAM + 5 GiB 显存。Windows 可用物理内存与系统提交余量共同约束 RAM；DXGI 本地预算与独显实际容量共同约束本地 GPU 内存。各自保留安全余量，不固定 RAM 与显存比例。

非本地 GPU 内存只计入 RAM 一次；临时区、上传、回读、派生对象和在途分配也应计入账本。软线触发回收，优先回收已空闲或可重建内容；硬线限制新增。预算骤降时允许受 Pin/Fence 保护或持有唯一权威的旧分配暂时超线，停发超限额度，不提前释放。受管账本、进程占用和设备占用须分别测量。开场准入的正例不证明游戏内峰值、压力下回收能力或驻留收益。

## 验收与 Windows 发布

1. **先达到可玩。** 按开始后进入有代表性、可控制的游戏场景，连续 10 分钟无崩溃或明显画面错误，并可复现。记录实际运行的源码提交、构建标识及启动路径、硬件、场景、日志、RAM/显存峰值和帧时间。不设未经实测的 FPS 门槛；10 分钟也不代表长期没有内存增长。开场或菜单、通过编译、合成夹具通过均不能替代此项。当前状态见[证据页](vnme-evidence.md#当前实机基线)。
2. **再发首个可核验的 Windows 版。** 验过实际交付构建及其启动路径，确认默认使用 VNME 且不靠 Shadow 回退，注明构建来源与已知限制，提供可下载的 Windows x64 包。不分发游戏原始文件（见[资料规则](asset-policy.md)）。若报告第一阶段进度，发布前不报 100%。Performance/Manual 预算模式产品化、主动迁移、多队列、大规模预转换及全面提速不是第一阶段前置条件。
3. **后用实测排序优化。** 同机、同场景、同设定与第一版对照，看慢帧分位、卡顿、真实 GPU/CPU 帧时间、Fence 等待、传输量、驻留命中与内存峰值。区分受管采样与进程/设备峰值，不能把 CPU 提交时长当作 GPU 帧时间。只采用能改善已测瓶颈、且不破坏正确性不变量的改动；验证收益与兼容性后发后续版本。
