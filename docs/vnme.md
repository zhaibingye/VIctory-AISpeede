# VNME 第三代架构与开发路线

本文是 VNME 的现行设计与验收入口，供开发者和本地并行代理使用。设计目标、代码接入和实机结果分别记录；实机结论只归于实际运行的提交，不以当前分支尖端代替。
[旧统一内存文档](unified-memory-engine.md)仅保留作历史；与本文冲突时以本文为准。

## 目标与当前取舍

让 Series S 游戏在 Windows 上保持可观察行为等价，优先照顾 RTX 3060 Laptop 6 GB、
16 GB RAM、i5-11260H 一类设备。保留 x86-64 原生执行、Loader、Xbox HLE、
Shader 翻译和 Pipeline 预编译。不复刻 Xbox 的实现过程；能直接用宿主操作就不重复转换。

Series S 的 10 GiB 逻辑统一内存和 7,776 MiB 标题报告值不变。**取消的是宿主写死的
10 GiB RAM + 5 GiB 显存，不是安全上限。** Windows 可用物理内存和系统提交余量决定
RAM 准入，DXGI 本地预算和显卡容量决定独显准入，各自保留安全余量。不会预占满，也不
固定两侧比例。非本地 GPU 内存计入 RAM 一次；临时区、上传、回读、派生和在途分配
都应进入账本。软线触发回收，硬线限制新增；预算骤降时允许受保护旧分配暂时账面超线，
停止新增并等待可安全回收，不能提前释放在途资源或唯一权威数据。受管预算不等于整机占用。

## 八项职责与代码入口

八项是逻辑职责，不要求八个 crate。以下路径是当前核对入口，不代表全覆盖。

| 职责 | 规则 | 当前代码入口与边界 |
| --- | --- | --- |
| 统一地址与身份 | 64 KiB 页作为内存身份基础；别名归到物理身份，重绑和复用不继承旧内容。原生纹理不必按页存储。 | `victory-memory` 的 `guest.rs`、`physical.rs`、`virtual_pages.rs`，以及 `victory-gpu/src/title_backing.rs`。页身份能证明地址关系，不能独立证明纹理已被写入。 |
| 原生表示 | 不需要 CPU 读原始字节时，优先用宿主原生对象；需要保留精确字节时，在同一引擎内用字节兼容表示。 | `victory-gpu/src/page_resource.rs`、`page_texture.rs`。只读缓存和在途快照可临时并存，不得成为第二份权威。 |
| 操作翻译 | 将绘制、清除、复制和采样尽量翻成对应的宿主操作，避免为一次操作重建整个资源。 | `victory-gpu/src/page_draw.rs`、`page_dispatch.rs`、`page_view.rs` 和 `victory-shader`。未知语义不能假装执行过。 |
| 权威与依赖 | 按资源和实际访问范围追踪写入，分别识别已提交、已完成及访问者何时能读。 | `victory-memory/src/authority.rs` 与 GPU 资源、队列代码。跨对象的局部版本号不可直接比较先后；别名不等于内容有效。 |
| 按需一致性 | 只向真正的消费者提供必要范围，不主动回读、不重复上传；仅在证明完整覆盖时跳过旧内容。 | `victory-memory/src/coherence.rs`、GPU `page_queue.rs`。CPU 原生指针读到 GPU 权威数据前，必须在真实访问或已知同步点保证可见；尚无通用覆盖证明。 |
| 异步提交 | 先把主 Direct Queue 的顺序和 Fence 做对，让没有依赖的工作重叠，不提前报完成。 | `victory-gpu/src/title_timeline.rs`、`page_queue.rs` 与 `victory-memory/src/timeline.rs`。已有提交路径，不代表所有等待都已消除。 |
| 动态驻留和预算 | 按预算准入、按需扩容和复用，优先回收空闲或可重建内容，遵循 Pin/Fence。 | `victory-memory/src/budget/`、`residency.rs` 和 GPU `page_slabs.rs`。已观察到准入随压力变化；真实游戏的峰值、压力回收和驻留收益仍待验。 |
| 原生资源缓存 | 沿用着色器和管线缓存，再按实际开销扩展预转换；校验内容、格式与转换版本，必要时匹配设备和驱动。 | `victory-pipeline`、`victory-shader` 和 GPU `shader_cache.rs`。现有缓存不等于完整的原生纹理与几何缓存；不持久化不透明显存布局。 |

一条典型的数据路径是：来宾命令 → 解析页身份、别名和访问范围 → 选择原生或字节兼容表示
→ 确认当前权威与依赖 → 预算准入并保活 → 按队列顺序执行 → 在真实 Fence 条件满足后
公开结果或回收。CPU 需要 GPU 结果时才处理可见性；GPU 内部依赖优先在 GPU 内解决。

**生产方向只有一套 VNME。** 现有代码仍用 `paged-title` 显式选择实验路径，仓库里依然
有旧渲染代码；不能把它描述成已完成切换，也不能在 VNME 出错时静默跳回 Shadow Buffer。
可以重构掉错误抽象，但不伪造 Fence、清空实际应保留的内容、跳过写入或拿同尺寸纹理凑数。

## 第一阶段：先跑通，再发可核验的 Windows 版

1. **当前优先项是开始后崩溃。** `13eee34` 与 `b40a245` 已在目标 Windows 机器上
   复现：触发开始后，`draw` 索引 15 读取 3840×2160 颜色目标的旧内容时，在编码阶段报
   `MissingTextureContent`。未记录同键前代或已验证的兼容字节来源。`b40a245` 还确认
   失败批次的已编码前缀没有来宾字节复制、显式纹理上传或纹理复制；当前目标可识别 510 个
   物理页，但保留的历史不完整，不能排除更早的提交、物理别名或其它字节写入。
   已见的同目标屏障不是生产者，不能把纹理置空。先证明写入者、分配生命周期、覆盖范围、
   布局和提交顺序，再选择可证的内容恢复路径。诊断和离线结果不代表已修复或已可玩。
2. **跑通门槛**：按开始后进入有代表性、可控制的游戏场景，连续 10 分钟无崩溃或
   明显画面错误，并可复现。记录提交、构建标识、硬件、场景、日志、RAM/显存峰值和
   帧时间；不设拍脑袋的 FPS 门槛。10 分钟用于可玩验证，不代表长期无内存增长。
3. **发版门槛**：验过实际选用的构建和启动路径，说明已知限制；确认默认 VNME 不靠
   Shadow 回退，再交付可下载的 Windows x64 包，记录构建来源。进度百分比只指
   第一阶段，发布前不报 100%；编译、夹具和真游戏是三类各自独立的证据。
4. **暂缓项**：Performance/Manual 预算模式的完整产品化、主动迁移策略、多队列、
   大规模预转换、GPU/Shader 全面提速。它们不是第一阶段前置条件。需要排期时先拿到
   可重现的正确性或性能证据。

## 第二阶段：对照实测找瓶颈，择优优化再发版

以同机、同场景和同设定对照第一阶段。优先看慢帧分位、卡顿次数、真实 GPU/CPU 帧时间、
Fence 等待、传输字节、驻留命中和 RAM/显存峰值；区分受管采样与进程/设备峰值，不把
CPU 提交计时当作 GPU 帧时间。参考 `fxceless/victory-fork` 的 `victory-gpu` 和
`victory-shader` 思路，只采纳能解决已测瓶颈且符合 VNME 不变量的改动。不整库合并，
不恢复旧后端。验证收益和兼容性后发第二版，再按实机发现继续迭代。

## 本地并行开发与交接

- 一个整合者负责共享分支。子代理各用独立 Git worktree 和分支，先对齐基线；
  建议分为「队列与权威」「物理身份与别名」「夹具和日志」。前两条若同时触碰同一状态
  更新接口，先给出证据和接口约定，再由整合者负责修改。不要并发推同一分支或强推。
- 每条交付注明仓库、分支、完整基线和改动 SHA、命令和结果、是否实机，以及同步状态
  （仅工作区 / 已提交 / 已核验远端）。实机报告写实际运行的包和日志，不以当前分支尖端代替。
- 开发中优先基础静态检查。只有证明资源语义、检验 GPU 提交或卡住可玩验收时，才做
  有目的的夹具或实机验证。固定构建和日志，失败先保留首因，不反复跑已知坏包。
- 面向用户的说明、配置注释和日志默认中文；保留命令、配置键、错误标识。默认
  `cache` 与 `data` 放在可执行文件所在目录，不迁移既有用户数据。游戏原始文件
  不改动，也不随包或代码库分发。
